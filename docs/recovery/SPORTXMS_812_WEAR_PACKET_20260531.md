# Mi Band 9 SportXms/812 lower send packet extraction — 2026-05-31

## Bottom line

Static Mi Fitness analysis now reaches the first real Xiaomi wearable command object below the SportXms Binder layer.

The `startSport(812)` route ultimately sends a protobuf-nano-style `hns` packet through Xiaomi `DeviceContact` / `DeviceSyncManager`, not a simple BLE GATT write and not the Binder parcel itself.

```text
SportXms Binder startSport(812)
→ SportXmsApiImpl.startSport(...)
→ ISportRemoteState.startSport(...)
→ SportWearSender / cgp.l(...)
→ DeviceSyncManager.call(did, hns, needResponse=true, timeout=15s)
→ Xiaomi session/framing/encryption transport
→ band enters SportXms/812 sensor mode
```

This is still not enough for pure macOS direct, because `DeviceContact` adds Xiaomi transport/session framing. But it is the missing semantic command shape we needed to target dynamic hooks or a Gadgetbridge port.

## Minimal plaintext command skeleton

Before Xiaomi `DeviceContact` transport/session wrapping, the logical command is:

```text
hns {
  1: 8,
  2: 26,
  10: uca {
    20: hfa {
      1: timestamp_seconds,
      2: oe4 { 1: timezone_15min_or_app_value },
      3: 812,
      4: 0,
      6: 3
    }
  }
}
```

For Shanghai timezone offset (`UTC+8 = 32` if encoded as 15-minute units) and a sample timestamp, the plain protobuf-like payload generated by a local encoder was:

```text
hns_hex = 08 08 10 1a 52 14 a2 01 11 08 87 89 f0 d0 06 12 02 08 20 18 ac 06 20 00 30 03
```

The Android Gadgetbridge-native opener must preserve that `field2` shape. A failed early opener wrote timezone as a bare varint and produced a 24-byte payload; the successful live opener writes `hfa.field2` as an `oe4` submessage (`12 02 08 20`) and produces a 26-byte `vga.v()`-parity payload. In the 2026-06-01 live run, that 26-byte payload over Gadgetbridge encrypted SPP V2 `Channel.ProtobufCommand` produced `8/26=1`, `8/50=9`, and `8/53=95` packets in a 10s capture window.

Do **not** send this exact hex as-is:

- timestamp must be current;
- timezone must match Mi Fitness' actual value;
- `DeviceContact` wraps/fragments/encrypts the payload;
- Xiaomi app-layer session must already be initialized.

## Stop command parity and live result

Mi Fitness uses the same `hns(type=8, subtype=26, uca.field20=hfa)` envelope for SportXms stop/finish. The difference is only `SportRequestData.sportState` → `hfa.field4` through `vga.x(...)`:

```text

app sportState=2 → hfa.field4=1  # pause-ish
```

## First 8/53 packet layout

The working start stream produces `hns(type=8, subtype=53)` packets. The prefix decoder added at `tools/miband9ctl/decode_xms53_packets.py` confirms this protobuf shape from the existing live artifact:

```text
hns.field1 = 8
hns.field2 = 53
hns.field10 = uca
uca.field15 = fga
fga.field5 = repeated ee4 samples
```

Mi Fitness types:

```text
uca.field15 → fga
fga.field5 / field6 → repeated ee4

ee4.field1 → uint64-ish timestamp / tick
ee4.field2 → float32 x
ee4.field3 → float32 y
ee4.field4 → float32 z
```

Older hfimucli artifacts truncated `payload_hex` prefixes to 64 bytes, so the first decoder pass only saw the first two complete samples in each logged packet prefix. The declared lengths still inferred full packets of 20 `ee4` entries each (`uca.field15 declared length = 480`, repeated sample item = 24 bytes including tag+len).

Example decoded prefix from `/tmp/miband9_type101_parity_20260601_000928/open_counter_live.json`:

```text
packets=95
inferred_samples_per_full_packet=20
first sample: t=193187029500, x=-9.5426, y=0.1795, z=0.5271
```

The axes looked like accelerometer-scale float triplets, not merely ACK/status bytes. The follow-up full-payload pass below confirms the missing second half is gyroscope data, not another status field.

## Remaining unknowns

Pure Mac direct still needs the rest of the Xiaomi transport, but the first lower layer is now identified:

```text
DeviceContact.call(did, hns, needResponse, callback, timeout)
→ wearable API type 101
→ encrypted PB/protobuf channel 1
→ L2 opcode 2 (WRITE_ENC)
→ L1 A5A5 session frame + CRC/seq/window
→ BLE V2 SAR write/notify path, or SPP V2 ProtobufCommand channel
```

The transport details and Gadgetbridge porting seam are now documented in:

- `docs/recovery/DEVICECONTACT_TRANSPORT_TRACE_20260531.md`
- `tools/miband9ctl/gadgetbridge_port_skeleton/XiaomiSportXms812Command.java`

The next high-yield hook point is above encryption:

- `DeviceContact.call(...)`
- `DeviceSyncExtKt.getInstance(...).call(...)`
- `SportDeviceModel.INSTANCE.getDeviceSyncManager().call(...)`
- protobuf `hns.j(...)` serialization output, if hookable

The next lower hook point is after transport wrapping:

- BLE characteristic writes in Xiaomi device contact stack
- HCI/btsnoop aligned around `sport_started` and first `sensor_packet`

## Porting implication

For Gadgetbridge-native first, we do **not** need to recreate the entire Mi Fitness UI. We need a Gadgetbridge-side equivalent of:

```text
build hns(e=8, f=26, uca.field20=hfa(812,start,tz,timestamp,selectVersion=3))
→ send through Gadgetbridge Xiaomi authenticated/session transport
→ parse matching sensor/status responses
```

macOS direct comes after this, because CoreBluetooth still needs Gadgetbridge-equivalent Xiaomi auth/session/framing.
